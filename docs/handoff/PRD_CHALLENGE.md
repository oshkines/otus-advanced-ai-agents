> **Версия:** 1.0 · **Дата:** 02.11.2026 · **Статус:** готово к передаче в Phase 6.
> **Владелец продукта:** Евгений (senior C++/1C инженер, единственный пользователь дашборда).
> **Связанные документы:** `design.md` §5–§10,
> `.planning/phases/phase-05-bento-dashboard/{DISCUSS,DESIGN,CONTRACT}.md`,
> `docs/research/BENCHMARKING.md`.
>

## 1. Персоны и контекст

|---|---|---|---|

| **Сын** | Студент Алфёровского университета | Уехать на каникулы 26.12.2026 и вернуться 09.01.2027 | Даты фиксированы; покупает отец |

## 2. Глоссарий и статусы

| Термин | Значение |
|---|---|
| **Канал** | Модуль дашборда: Email, Вакансии, РЖД. Описан в `ui.dashboard.navigation`. |
| **Воркер** | Python-процесс, который собирает данные канала (Phase 6). |
| **Вердикт** | Результат ИИ-классификации письма: `apply` (ответить), `review` (проверить), `ignore` (в архив), `spam`. |
| **`active`** | Воркер канала найден и `enabled: true`. |
| **`disabled`** | Воркер найден, но `enabled: false`. |
| **`not_connected`** | Воркера канала нет в `workers[]`. Страница всё равно рендерится. |
| **`ConfigError`** | Конфиг не прочитан/не прошёл валидацию. Ошибка показывается баннером, навигация остаётся. |
| **MOCK** | Данные-заглушки до появления воркера; всегда помечены бейджем. |

## 3. Эпик A — Почта (Email)

### US-EM-01. Статус почтовых ящиков на обзоре

**Как** инженер Евгений, **я хочу** видеть статус подключения почтовых ящиков на главном экране,
**чтобы** за 2 секунды понять, работает ли сбор писем и не заблокирован ли IMAP.

**Acceptance Criteria**

- **AC-1 (Given/When/Then).** *Given* воркер `email_watcher` есть в конфиге и `enabled: false`,
  *When* открываю `/`, *Then* карточка Email показывает `StatusBadge` с текстом «выключен»,
  точкой `--color-idle` и `data-status="disabled"`.
- **AC-2.** *Given* воркер `enabled: true`, *When* открываю `/`, *Then* статус `active`:
  текст «активен», точка `--color-success-soft` (#3FB950), `data-status="active"`.
- **AC-3.** *Given* воркера нет в `workers[]`, *When* открываю `/` и `/email`,
  *Then* статус `not_connected` (текст «не подключён», `--color-warning`), страницы рендерятся,
  в сайдбаре пункт Email остаётся.
- **AC-4.** *Given* конфиг недоступен, *When* открываю `/`, *Then* появляется
  `ConfigError` (`data-testid="config-error-banner"`), сайдбар показывает заглушки модулей,
  карточки каналов не исчезают, страница не отдаёт 500/белый экран.
- **AC-5.** Статус никогда не передаётся только цветом: рядом всегда есть текст.

**Статус в Phase 5:** реализовано (Config-SSR + MOCK).

### US-EM-02. ИИ-вердикты по письмам

**Как** Евгений, **я хочу** видеть вердикт и короткую причину по каждому письму, **чтобы**
решать, что требует ответа, а что можно заархивировать, не открывая письмо.

**Acceptance Criteria**

- **AC-1.** На `/email` каждый элемент списка показывает: отправителя, тему, время,
  вердикт и причину вердикта (одна строка).
- **AC-2.** Вердикты `apply` / `review` / `ignore` / `spam` имеют разные текстовые подписи
  («ответить», «проверить», «в архив», «спам») и разные тона: `success`, `warning`, `muted`, `danger`.
- **AC-3.** Счётчики сверху: «Всего писем», «Требуют ответа» (apply + review), «Отклонено»
  (ignore + spam). Сумма категорий равна общему числу.
- **AC-4.** Причина вердикта — текст, а не иконка; скринридер читает вердикт вместе с письмом.
- **AC-5.** В списке нет эмодзи; иконки — только инлайн-набор проекта.

**Статус в Phase 5:** реализовано на MOCK-данных (`lib/mock/emails.ts`).

### US-EM-03. Запрос полного письма (Optimistic UI)

**Как** Евгений, **я хочу** запросить полный текст письма и видеть шаги обработки, **чтобы**
не думать, завис ли агент, и не нажимать кнопку повторно.

**Acceptance Criteria**

- **AC-1.** *Given* карточка письма, *When* нажимаю «Полное письмо», *Then* кнопка
  переходит в `data-state="pending"`, получает `aria-busy="true"` и `disabled`.
- **AC-2.** Во время ожидания последовательно отображаются шаги:
  «Выкачиваю тело письма…» → «Генерирую саммари DeepSeek-R1…» → «Готово». Список шагов
  имеет `aria-live="polite"` (не перебивает пользователя).
- **AC-3.** По завершении `data-state="success"`, кнопка снова активна, текст
  «Саммари готово». Повторный клик во время `pending` невозможен.
- **AC-4.** *Given* браузер offline, *When* нажимаю кнопку, *Then* через ≤ 300 мс
  `data-state="error"`, сообщение «Нет сети: запрос не отправлен. Повторите, когда соединение
  восстановится», кнопка «Повторить»; введённые/выбранные данные не сбрасываются.
- **AC-5.** После ошибки фокус остаётся на кнопке; сообщение доступно скринридеру (`role="alert"`).

**Статус в Phase 5:** реализовано в UI (`components/interactive/OptimisticAction.tsx`),
сетевой вызов — заглушка до Phase 6.

### US-EM-04. Диагностика блокировки IMAP / РКН

**Как** Евгений, **я хочу** видеть причину недоступности почты и кнопку повтора, **чтобы**
отличить блокировку провайдера от ошибки пароля.

**Acceptance Criteria**

- **AC-1.** При таймауте соединения карточка канала получает тон `danger`, а текст ошибки
  выводится моноширинным шрифтом с кодом (`IMAP_TIMEOUT`, адрес сервера, длительность).
- **AC-2.** Текст понятен без логов: «Mail.ru недоступен (таймаут соединения).
  Авто-переподключение через 30 с».
- **AC-3.** Кнопка «Повторить» инициирует повторную попытку; во время попытки —
  `aria-busy="true"`, повторные клики заблокированы.
- **AC-4.** Уже загруженные письма остаются на экране (partial-состояние), список не очищается.
- **AC-5.** Секреты и тексты писем в лог ошибки не попадают: только имена переменных окружения.

**Статус в Phase 5:** контракт состояния готов; реальный IMAP — Phase 6 (`agents/mail_worker.py`).

### US-EM-05. Доступность списка писем

**Как** Евгений, работающий с клавиатуры, **я хочу** доходить до кнопок действия без мыши,
**чтобы** не терять контекст и скорость.

**Acceptance Criteria**

- **AC-1.** Список писем — семантический `ul`/`li`; для каждой строки доступны отправитель,
  тема и вердикт в порядке чтения.
- **AC-2.** Все интерактивные элементы достижимы `Tab`, имеют видимое фокус-кольцо
  (`focus-visible:ring-2`, `--color-primary`).
- **AC-3.** Кнопка действия имеет доступное имя («Полное письмо: <тема>»), а не только иконку.
- **AC-4.** Статус и вердикт озвучиваются текстом; `aria-live` используется только для
  результатов действий, не для декоративных обновлений.

**Статус в Phase 5:** реализовано.

## 4. Эпик B — Вакансии

### US-VC-01. Теги фильтра из конфига

**Как** Евгений, **я хочу** видеть, по каким тегам сканер ищет вакансии, **чтобы** понимать,
почему в списке нет нужной позиции.

**Acceptance Criteria**

- **AC-1.** *Given* `workers[vacancy_scanner].args = ["--tags", "C++, 1C, Remote"]`,
  *When* открываю `/vacancies`, *Then* карточка «Теги фильтра» показывает три тега:
  `C++`, `1C`, `Remote` (моноширинным шрифтом).
- **AC-2.** *Given* в `args` нет `--tags`, *When* открываю страницу, *Then* выводится
  текст «В args воркера теги не заданы», страница не падает.
- **AC-3.** *Given* воркера нет в конфиге, *When* открываю `/vacancies`, *Then* статус
  `not_connected`, теги берутся из резервной навигации, MOCK-бейдж видим.

**Статус в Phase 5:** реализовано.

### US-VC-02. Список вакансий и зарплатная вилка

**Как** Евгений, **я хочу** видеть компанию, стек, вилку, источник и дату, **чтобы**
отсеивать неподходящие вакансии без перехода на сайт.

**Acceptance Criteria**

- **AC-1.** Каждая вакансия содержит: название, компанию, стек, вилку, источник, дату.
- **AC-2.** Вилка выводится моноширинным шрифтом и тоном `success`; нулевая/скрытая вилка —
  текстом «вилка не указана», без пустого места.
- **AC-3.** *Given* ни одной вакансии не найдено, *When* открываю страницу, *Then* показывается
  `EmptyState` «Система в режиме ожидания. Новых событий не обнаружено» и подсказка,
  какие теги проверялись.
- **AC-4.** *Given* сканер упал, *When* открываю страницу, *Then* показывается последняя
  успешная выборка с меткой времени («данные на 02.11.2026 09:14») и предупреждением,
  а не пустой экран.

**Статус в Phase 5:** AC-1/AC-2/AC-3 — реализовано на MOCK; AC-4 — контракт состояния
(реальные ошибки сканера появятся в Phase 6).

### US-VC-03. Сортировка и фильтр (COULD)

**Как** Евгений, **я хочу** отсортировать вакансии по дате или вилке, **чтобы** быстрее
находить лучшие предложения.

**Acceptance Criteria**

- **AC-1.** Сортировка переключается кнопками «дата» / «вилка»; выбор отражается в URL
  (`?sort=salary`), чтобы ссылку можно было сохранить.
- **AC-2.** При смене сортировки фокус остаётся на активной кнопке, список не перезагружается
  в белый экран.
- **AC-3.** Пустой результат после фильтра даёт `EmptyState` с кнопкой «Сбросить фильтр».

**Статус в Phase 5:** backlog (COULD), не блокирует приёмку.

### US-VC-04. Прозрачность источника данных

**Как** Евгений, **я хочу** видеть, откуда взяты вакансии и когда обновлялись, **чтобы**
не принимать устаревшие данные за свежие.

**Acceptance Criteria**

- **AC-1.** В карточке канала указан воркер (`vacancy_scanner`), cron и `timeout_sec`.
- **AC-2.** MOCK-данные помечены бейджем «MOCK-данные» с указанием Phase 6 как источника.
- **AC-3.** Метка времени обновления выводится моноширинным шрифтом (`--font-mono`).

**Статус в Phase 5:** реализовано.

## 5. Эпик C — Билеты РЖД (каникулы сына, Алфёровский университет)

### US-RZ-01. Параметры мониторинга направления

**Как** отец, **я хочу** видеть, что именно мониторится (направление, типы вагонов, повод, cron),
**чтобы** быть уверенным: система ищет билеты на нужные даты, а не «что-то вообще».

**Acceptance Criteria**

- **AC-1.** *Given* `workers[rzhd_watcher].args` содержит `--from SPB --to MSK
  --car-types coupe,platzkart,sv --purpose university-holidays`,
  *When* открываю `/rzhd`, *Then* карточка «Параметры мониторинга» показывает
  `SPB → MSK`, `coupe,platzkart,sv`, `university-holidays` и cron воркера.
- **AC-2.** *Given* аргумента нет, *When* открываю страницу, *Then* выводится «—»,
  страница не падает.
- **AC-3.** Значения выводятся моноширинным шрифтом (`--font-mono`), чтобы `coupe,platzkart,sv`
  не переносился по слогам.
- **AC-4.** Окно каникул (26.12.2026 — 09.01.2027) отображается явно; даты не «зашиты» в UI-текст
  ошибки, а берутся из одного источника (`lib/mock/rzhd.ts`, позже — из воркера).

**Статус в Phase 5:** реализовано (параметры из конфига + окно каникул из MOCK-модуля).

### US-RZ-02. Свободные места и типы вагонов

**Как** отец, **я хочу** видеть свободные места по типам вагонов (купе / плацкарт / СВ),
**чтобы** выбрать компромисс между комфортом и ценой.

**Acceptance Criteria**

- **AC-1.** На `/rzhd` каждый рейс показывает: направление, дату, поезд, тип вагона
  («Купе» / «Плацкарт» / «СВ») и число свободных мест.
- **AC-2.** Сводная карточка «Свободных мест» показывает сумму по всем рейсам.
- **AC-3.** *Given* у рейса 0 мест, *When* открываю страницу, *Then* рейс **не скрывается**:
  метка «мест нет» тоном `danger`, кнопка покупки `disabled`.
- **AC-4.** Числа выровнены и выведены моноширинным шрифтом; единицы измерения не теряются.

**Статус в Phase 5:** реализовано на MOCK; источник — `rzhd_watcher` в Phase 6.

### US-RZ-03. Цена и тренд

**Как** отец, **я хочу** видеть минимальную цену и направление изменения, **чтобы** понять,
стоит ли ждать или покупать сейчас.

**Acceptance Criteria**

- **AC-1.** Карточка «Минимальная цена» показывает самое дешёвое предложение в рублях
  с разделителем разрядов (`4 820 ₽`).
- **AC-2.** Тренд передаётся **текстом и цветом**: «цена растёт» (`danger`), «цена падает»
  (`success`), «цена стабильна» (`muted`). Только цветом — запрещено.
- **AC-3.** *Given* данных о цене нет, *When* открываю страницу, *Then* выводится «—»,
  а не `Infinity`/`NaN`.

**Статус в Phase 5:** реализовано.

### US-RZ-04. Покупка билета: форма пассажира + Optimistic UI

**Как** отец, **я хочу** оформить билет в два шага, не теряя введённые данные и видя прогресс,
**чтобы** не пропустить места из-за зависшего интерфейса.

**Acceptance Criteria**

- **AC-1.** *Given* рейс с местами, *When* нажимаю «Купить билет», *Then* раскрывается форма
  пассажира (имя + дата поездки) **без перехода на другую страницу**; фокус переходит
  в поле «Имя пассажира» (программный фокус — единственный допустимый случай).
- **AC-2.** *Given* поле в фокусе, *When* ухожу из него (Tab/клик), *Then* валидация
  запускается по `blur`: ошибка появляется под полем, значение сохраняется,
  `aria-invalid="true"`, `aria-describedby` указывает на текст ошибки.
- **AC-3.** *Given* имя короче 2 символов, *When* отправляю форму, *Then* фокус возвращается
  в первое невалидное поле, форма не отправляется, введённые данные не сбрасываются.
- **AC-4.** *Given* форма валидна, *When* отправляю, *Then* кнопка переходит в
  `data-state="pending"`, `aria-busy="true"`, отображаются шаги:
  «Проверяю свободные места…» → «Бронирую…» → «Подтверждаю…»; повторный клик невозможен.
- **AC-5.** *Given* браузер offline или ошибка сети, *When* отправляю, *Then*
  `data-state="error"`, сообщение «Нет сети: бронь не отправлена. Данные формы сохранены»,
  кнопка «Повторить», значения полей на месте.
- **AC-6.** Даты поездки вне окна 26.12.2026 — 09.01.2027 отклоняются с подсказкой
  «Мониторинг настроен на каникулы 26.12.2026 — 09.01.2027».

**Статус в Phase 5:** реализовано в UI (`components/interactive/BlurValidatedForm.tsx` +
`OptimisticAction.tsx`); реальная бронь — Phase 6 (`rzhd_watcher`).

### US-RZ-05. Обратный отсчёт до каникул

**Как** отец, **я хочу** видеть, сколько дней осталось до выезда, **чтобы** не пропустить
старт продаж и дедлайн.

**Acceptance Criteria**

- **AC-1.** Карточка показывает «До выезда: N дней» (или «Сегодня» при N = 0).
- **AC-2.** *Given* дата выезда в прошлом, *When* открываю страницу, *Then* выводится
  «Каникулы начались» без отрицательных чисел.
- **AC-3.** Расчёт выполняется на сервере по Europe/Moscow, чтобы не зависеть от часов
  пользователя.

**Статус в Phase 5:** реализовано («До выезда» от фиксированного окна каникул);
открытие продаж и точные даты — из API в Phase 6.

## 6. Сквозные требования

| # | Требование | Критерий приёмки |
|---|---|---|
| X-01 | Палитра | Только токены `design.md` §2: canvas `#0A0E17`, surface `#161B22`. Slate-значения и `Consolas` в проекте отсутствуют (проверка grep). |
| X-02 | Типографика | Числа, пути, cron, коды ошибок и логи — `--font-mono` (JetBrains Mono). |
| X-03 | Статусы | Каждый статус = точка + текст + `data-status`; цвет не единственный носитель смысла. |
| X-04 | Фокус | Все интерактивные элементы имеют `focus-visible:ring-2`; порядок табуляции совпадает с визуальным. |
| X-05 | Motion | 200 ms, `cubic-bezier(0.4, 0, 0.2, 1)`; при `prefers-reduced-motion` анимации отключены. |
| X-06 | Локализация | Все пользовательские строки — на русском; в `config/orchestrator.json` кириллицы нет. |

## 7. End-to-End UX обработки ошибок

### 7.1 Потеря фокуса формы (focus loss)

**Сценарий.** Евгений открывает форму пассажира на `/rzhd`, вводит «Иван Петров», затем
кликает в поле даты или переключается в другое окно. Классический баг: `blur`-обработчик
сбрасывает значение или показывает модалку, и данные теряются.

**Ожидаемое поведение (шаг за шагом).**

1. **Blur по полю.** Валидация запускается только для **этого** поля. Остальные поля не трогаются.
2. **Значение сохраняется.** Ни `value`, ни позиция каретки не сбрасываются; повторный фокус
   возвращает курсор в конец введённого текста.
3. **Ошибка — inline.** Текст появляется под полем, связано через `aria-describedby`,
   поле получает `aria-invalid="true"`. Ошибка не перекрывает другие поля.
4. **Фокус не захватывается.** Никаких `alert()`, автоскроллов и принудительного возврата фокуса
   на `blur`: пользователь сам решает, куда идти.
5. **Ошибка не мигает.** При повторном фокусе она остаётся, пока значение не станет валидным;
   исчезает сразу после исправления (без «прыжков» layout — резервируется строка под текст).
6. **Уход из окна (`window.blur`).** Ничего не происходит: ни сброса, ни сохранения «наполовину».
   Форма остаётся в том же состоянии.
7. **Отправка невалидной формы.** Фокус программно переводится в **первое** невалидное поле,
   `aria-live` сообщает «Проверьте выделенные поля», значения остаются.
8. **Escape.** Скрывает inline-подсказку, но **не** очищает значение; повторный blur покажет
   ошибку снова, если поле всё ещё невалидно.
9. **Офлайн.** Отправка переводится в `error`-состояние с текстом «Нет сети: бронь не отправлена.
   Данные формы сохранены»; значения полей не сбрасываются, доступна кнопка «Повторить».

**Чего НЕ делаем:** не очищаем поле по blur, не показываем `window.alert`, не блокируем
переход фокуса, не скрываем ошибку до следующего сабмита, не сбрасываем форму после ошибки сети.

**Реализация:** `web/components/interactive/BlurValidatedForm.tsx`.
**Якоря:** `passenger-form`, `passenger-name`, `passenger-name-error`, `passenger-date`,
`passenger-date-error`, `passenger-form-status`.

### 7.2 Полная недоступность сети и `ConfigError`

Отказ может произойти на трёх уровнях. Для каждого — своё состояние и свой текст.

| Уровень | Что случилось | Что видит пользователь | Что работает |
|---|---|---|---|
| **L1. Браузер offline** | `navigator.onLine === false` | Баннер `OfflineBanner`: «Нет сети: действия недоступны, данные остаются на экране» (`role="status"`, `aria-live="polite"`) | Навигация по уже загруженным страницам, чтение данных, фокус |
| **L2. Конфиг не прочитан** | `ENOENT` / `EACCES` / невалидный JSON | `ConfigError`: «Конфиг orchestrator.json не прочитан», причина моноширинным, путь, подсказка, кнопка «Повторить» | Сайдбар (заглушки каналов), навигация, страницы каналов с MOCK |
| **L3. Сервер/рендер упал** | исключение в Server Component или клиентском дереве | `RouteError`: «Экран не удалось отрисовать», digest ошибки, «Повторить», «На главную» | Оболочка уровня `error.tsx` / `global-error.tsx` в палитре проекта |

**Acceptance Criteria**

- **AC-1.** *Given* браузер offline, *When* пользователь нажимает действие, *Then* оно завершается
  `error`-состоянием за ≤ 300 мс, без «вечного» `pending`.
- **AC-2.** *Given* конфиг не прочитан, *When* открываю `/`, *Then* видны `ConfigError`,
  заглушки навигации и объяснение, что bento строится из `ui.dashboard.navigation`.
- **AC-3.** *Given* ошибка уровня L3, *When* открываю маршрут, *Then* нет белого экрана:
  фон `#0A0E17`, читаемый текст, кнопки «Повторить» и «На главную».
- **AC-4.** Кнопка «Повторить» вызывает `router.refresh()` (L2) или `reset()` (L3) и не теряет
  текущий маршрут.
- **AC-5.** Ошибка **не скрывается** автоматически: если причина не устранена, баннер остаётся.
- **AC-6.** Текст ошибки копируется: `font-mono`, `break-all`, без обрезки.

**Реализация:** `components/states/ConfigError.tsx`, `components/states/OfflineBanner.tsx`,
`components/states/ReloadButton.tsx`, `app/error.tsx`, `app/global-error.tsx`.

### 7.3 Грациозная деградация без белого экрана

**Правила, которые обязаны выполняться всегда.**

1. **Layout не зависит от конфига.** Сайдбар, баннер и `<main>` рендерятся даже при полностью
   недоступном `orchestrator.json`.
2. **Блоки изолированы.** Ошибка одного канала не уносит соседние карточки: каждая карточка —
   самостоятельная `section` в bento-сетке.
3. **MOCK помечен.** Пользователь всегда видит, что данные не боевые (бейдж «MOCK-данные»).
4. **У каждого состояния есть следующий шаг.** Empty → что произойдёт дальше; Error → «Повторить»;
   Partial → «Обновить».
5. **Никакого белого экрана.** Любое исключение выше уровня страницы ловит `app/error.tsx`;
   исключение в корневом layout — `app/global-error.tsx` с inline-стилями (глобальный CSS может
   быть недоступен).
6. **Никаких «голых» страниц.** Неизвестный маршрут — `not-found.tsx` с навигацией и объяснением.
7. **Ошибка не исчезает сама.** Автоскрытие через таймер запрещено: причина должна быть устранена.

**Acceptance Criteria**

- **AC-1.** *Given* в конфиге отсутствует `ui.dashboard`, *When* открываю `/`,
  *Then* применяется `DEFAULT_NAVIGATION` (Email / Вакансии / РЖД), страница рендерится.
- **AC-2.** *Given* конфиг не прочитан, *When* открываю `/email`, *Then* страница показывает
  MOCK-список и статус `not_connected`, а не 500.
- **AC-3.** *Given* исключение в клиентском компоненте, *When* происходит рендер,
  *Then* появляется `RouteError` (`data-testid="route-error"`) с кнопками «Повторить» и
  «На главную»; фон остаётся `#0A0E17`.
- **AC-4.** *Given* исключение в корневом layout, *When* открываю любой маршрут,
  *Then* `global-error` (`data-testid="global-error"`) показывает текст и ссылки, без белого фона.
- **AC-5.** *Given* неизвестный URL, *When* открываю `/does-not-exist`,
  *Then* `not-found` (`data-testid="not-found"`) показывает «Страница не найдена» и ссылки
  на «Обзор», «Email», «Вакансии», «РЖД».
- **AC-6.** Ни один сценарий не приводит к пустому `<body>` или экрану без текста.

**Как проверяем (failure injection).**

| Инъекция | Команда/действие | Ожидание |
|---|---|---|
| Конфиг отсутствует | Временно переименовать `config/orchestrator.json` → `orchestrator.json.bak` | `ConfigError`, заглушки навигации, 0 исключений |
| Битый JSON | Удалить закрывающую `}` в копии | `ConfigError` с причиной `Unexpected end of JSON input` |
| Исключение в компоненте | Временно `throw new Error("boom")` в карточке | Остальные карточки живы, `RouteError` (если ошибка выше) |
| Офлайн | DevTools → Network → Offline | `OfflineBanner`, действия → `error` ≤ 300 мс |
| Неизвестный маршрут | `/nope` | `not-found`, навигация работает |

### 7.4 Таймаут воркера и частичные данные (Partial)

**Сценарий.** `email_watcher` не уложился в `timeout_sec` (120 с) или `rzhd_watcher` — в 180 с.

**Ожидаемое поведение.**

- Канал переходит в состояние `warning` (не `danger`): таймаут — это деградация, а не поломка.
- Показываются **последние успешные данные** с явной меткой времени («данные на 02.11.2026 09:14»).
- Список не очищается; кнопка «Обновить» доступна.
- Текст: «Воркер не ответил за 120 с. Показаны данные последнего успешного запуска».
- Соседние каналы не затронуты.

**Acceptance Criteria**

- **AC-1.** Частичные данные визуально отличимы от свежих (метка времени + тон `warning`).
- **AC-2.** Повторный запрос не блокирует интерфейс: кнопка получает `aria-busy`, но страница
  остаётся интерактивной.
- **AC-3.** Если успешных данных ещё не было, показывается `EmptyState` с объяснением,
  а не пустая карточка.

### 7.5 Битый конфиг и ошибки валидации

**Сценарий.** JSON валиден, но структура не соответствует контракту (нет `workers`, `core.name`
не строка, `navigation[].id` пустой).

**Ожидаемое поведение.**

- `parseOrchestratorConfig()` выбрасывает `ConfigValidationError` со списком полей.
- UI показывает `ConfigError` с перечнем проблем (каждое поле — отдельной строкой, `font-mono`).
- Конфиг **не** применяется частично: дашборд не строится на полувалидных данных.
- Неизвестные (лишние) поля игнорируются — forward-compatible, как требует `CONTRACT.md` §1.
- Отсутствующие необязательные поля заполняются значениями по умолчанию в слое деривации.

**Acceptance Criteria**

- **AC-1.** Сообщение содержит имя поля и ожидаемый тип.
- **AC-2.** Приложение не падает и не показывает стектрейс пользователю (стек — только в консоль/лог).
- **AC-3.** После исправления конфига кнопка «Повторить» возвращает рабочий дашборд без рестарта
  процесса (в dev — с учётом сброса кэша).

### 7.6 404 и неизвестный маршрут

**Сценарий.** Пользователь ввёл `/rzhd-tickets` или перешёл по устаревшей ссылке.

**Ожидаемое поведение.**

- `app/not-found.tsx`: заголовок «Страница не найдена», объяснение, ссылки на все 4 раздела.
- Сайдбар остаётся, потому что `not-found` рендерится внутри корневого layout.
- HTTP-статус — 404, а не 200 и не 500.

**Acceptance Criteria**

- **AC-1.** Страница содержит `data-testid="not-found"` и минимум 3 рабочие ссылки.
- **AC-2.** Нет белого фона и «пустого» текста.
- **AC-3.** Переход по ссылке «Обзор» возвращает на `/`.
