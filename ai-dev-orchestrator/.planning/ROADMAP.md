# ROADMAP: AI Dev Orchestrator

Фреймворк: **gsd-core**. Единица планирования — фаза; внутри фазы — шаги, отражённые в `.planning/PROGRESS.md`.

Легенда статусов: `DONE` — завершена и проверена · `IN PROGRESS` — выполняется · `PLANNED` — запланирована.

---

## Phase 0 — Discovery `DONE`

**Цель:** выбрать стек, среду и инструменты ИИ-разработки, зафиксировать ограничения.

**Deliverables:**
- Стек зафиксирован под Windows 11 native: C++20 (MSVC 2022 + CMake), Python 3.11+, SQLite3.
- ИИ-среда: VS Code + Cline + DeepSeek (облако) + локальный DeepSeek-R1 14b через Ollama как резерв.
- MCP-сервер `context7` подключён для актуализации документации библиотек.
- Правила поведения агента: `CLAUDE.md`, `.clinerules`, режим по умолчанию `plan`.

**Exit criteria:** ✅ все пункты закрыты, ограничения записаны в `.clinerules` и `CLAUDE.md`.

## Phase 1 — Каркас репозитория и безопасность `DONE`

**Цель:** физическая структура проекта и защита секретов.

**Deliverables:**

- `config/orchestrator.json` — стартовая конфигурация (core, workers, storage, ui, e2e).

- Миграция документации в GSD-структуру `.planning/` (26.10.2026).

**Exit criteria:** ✅ e2e зелёный (exit code 0), `.env` агенту недоступен (Тест-маяк 1).

## Phase 2 — Разработка ядра C++20 `PLANNED`

**Цель:** консольное ядро, которое читает `config/orchestrator.json` и запускает Python-воркеры по расписанию.

**Deliverables:**
- `CMakeLists.txt` + `CMakePresets.json` (MSVC 2022, C++20, vcpkg).
- `src/main.cpp`: парсинг конфига, валидация схемы, логирование с timestamps.
- Планировщик (cron-подобное расписание из поля `schedule`), менеджер процессов воркеров с `timeout_sec`.
- Разбор JSON из `stdout` воркеров, запись результатов в SQLite3 (`data/cache.db`).
- Коды возврата и структурированные сообщения об ошибках.

**Exit criteria:** ядро собирается одной командой CMake, поднимает тестовый воркер-заглушку, корректно убивает его по таймауту.

**Зависимости:** Phase 1 (конфиг и каталоги).

---

## Phase 3 — Интеграция с Telegram `PLANNED`

**Цель:** воркер, который читает сообщения/уведомления и отдаёт нормализованный JSON в ядро.

**Deliverables:**
- `agents/telegram_watcher.py` (`aiogram`/`telebot`, строгая типизация).
- Секреты — исключительно из переменных окружения Windows (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`), уже прописаны в `env_required`.
- Дедупликация через SQLite-кэш, чтобы не слать повторы и не жечь токены.
- Мок-режим без сети для тестов (`--dry-run`), юнит-тесты на парсинг апдейтов.

**Exit criteria:** воркер отдаёт валидный JSON в `stdout`, при отсутствии токена завершается с понятной ошибкой (без хардкода), дубли отфильтрованы.

**Зависимости:** Phase 2 (ядро умеет запускать воркеры и читать их вывод).

---

## Phase 4 — Интеграция с Яндекс.Макс `PLANNED`

**Цель:** второй канал связи/уведомлений через платформу Яндекс.Макс (агент/бот).

**Deliverables:**
- `agents/yandex_max_worker.py` — адаптер к API Яндекс.Макс.
- Переменные окружения для токенов (`YANDEX_MAX_TOKEN`, `YANDEX_MAX_BOT_ID` — уточнить по актуальной документации на этапе планирования фазы; проверка через MCP `context7`).
- Унификация формата сообщений между Telegram и Яндекс.Макс на стороне ядра (общая схема JSON).
- Изоляция сбоев: падение канала не должно останавливать ядро и остальные воркеры.

**Exit criteria:** оба канала работают одновременно через единый контракт ядра; секреты только в окружении; есть e2e/интеграционный тест с моками.

**Зависимости:** Phase 3 (переиспользуем слой дедупликации и нормализации сообщений).
